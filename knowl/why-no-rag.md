# 为什么我们没有选择RAG的技术路线构建知识库？

昨天的招聘考核信息发出来以后，我们当晚就收到了一个 RAG 知识库的课题申请。

首先非常感谢这位候选人的积极性。但是我们也要泼一盆冷水，从方案里看是一个非常经典的 RAG 知识库，看到了我们知识膨胀的表面，但是没有看到我们已有的知识管理结构。整个方案可以看的出来对我们的思考和理解还比较表面。

为了解决这个问题，这篇文章解释为什么我们放弃了RAG这条路线，以及为什么市场越来越不把 RAG 作为主要选型。

## RAG只能解决知识检索而不能解决知识生产

早在大模型刚出来的时代，我们就在项目里尝试用过 RAG。我们发现经过基本的 RAG 方案之后，数据效果依然不是很好。

我们复盘以后觉得，RAG 不是银弹，最后还是要回到数据本身的结构优化，是搜索工程和数据工程的硬功夫。

后来我们试了很多通用的基于 RAG 的知识库，大多效果比较糟糕。包括飞书知识问答也是类似情况，基本上很难利用我们搭建的知识结构来获得更准确的信息。

从整个市场来看，应用 RAG 比较成功的通常是知识积累比较稳定成熟的企业，比如大型国企。我们的朋友中有成功的实践。类似的场景成功率可以达到 80-90%。

而我们这样处于前沿探索的小型科技企业则完全不同。我们的知识结构一直在快速变化，以适应整个市场最前沿的快速变化。因此大量的知识处在模糊和动态的状态。这样的场景成功率可以低到 45-60%。

大部分RAG的方案很难适应我们快速变化的原始知识库，也很难利用我们搭建的知识结构来符合我们的习惯。

## 我们选择使用LLM知识库的方式构建第二大脑

随着大模型上下文窗口急剧变大，和 DeepSeek、MiMo 等部分大模型成本的急剧下降，尤其是缓存输入的成本急剧下降，整个市场越来越发现 LLM 知识库的性价比更高，而且更适合与 AI 协作适应动态变化。

我们延续了我们在企业微信和飞书搭建知识库的习惯，精心搭建了一个 GitHub 仓库的 LLM 知识库。我们利用 Git 仓库建立单个知识库维护的物理围栏，利用 Git 子模块的机制把一系列知识库分层分组关联。

这套方案帮助我们在几个月内快速搭建了一个覆盖了公司十年知识积累的知识库，也促成了近两个月以来公司产能的大爆发。

随着公司知识库的扩大和 DeepSeek 的大涨，这套范式也在急剧地崩溃。确实是到了需要引入RAG的临界点。

但是绝对不应该是不考虑任何知识结构背景的 RAG。RAG 的好处是可以建立联想能力，如果能在现有的知识结构约束下找到 RAG 的合适位置，那是最理想的方案。

这个结构长什么样子，我们还没有完全想象出来。但是这个结构理应帮助我们提高知识库内部的一致性，并且降低知识库的维护成本。

最重要的是，我们一直采取白盒化的思维构建。目前的知识库已经开始逐渐膨胀到人类难以理解的程度。所以帮助人类专家理解和维护也是一个重大难题。
